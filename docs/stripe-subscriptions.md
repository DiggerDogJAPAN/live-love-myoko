### Database isolation within the same Supabase project

The revised, still-unapplied Finder 008 proposal retains the same three private forced-RLS tables and four service-only RPCs. `billing_settings.mode` defaults to `live`; only the database operator can switch it to `test`. Customer mappings are unique by `(user_id, livemode)` and `(customer_id, livemode)`. Subscription uniqueness, event receipts and their foreign keys also include mode. Changing runtime mode to live never copies test paid state into a live row. In-flight apply calls fail when database mode changes.

## Checkout, reconciliation and entitlement rules

- Authenticated, verified, active customers request Basic/Premium on their account page. Amounts, Price IDs, owner IDs, customer IDs and return URLs are selected server-side. Administrators cannot buy live subscriptions. Explicit Sandbox mode lets only verified active administrators create simulated subscriptions; ordinary customers receive no billing controls or provider state in that mode. There are no trial/payment bypass controls.
- A short database lease serializes operations per customer, using the same per-user advisory lock as privacy processing. Already processed event IDs return idempotently within their mode. An expired writer cannot apply its result or release a replacement lease.
- Before a new Checkout, read canonical subscriptions and recent sessions. Existing subscriptions go to the Portal; an open Checkout is reused for the same plan and blocks a second plan. Stable server idempotency keys recover ambiguous creation results. Multiple subscriptions or truncated provider lists require operator review instead of choosing an arbitrary entitlement.
- The success redirect grants nothing. Status refresh and signed webhook reconciliation obtain the current Stripe subscription, invoice/payment records and current attached schedule. Invoice proof must match the current customer, subscription, item, price, currency, quantity and service period. For positive amounts, paid InvoicePayment allocations backed by Stripe PaymentIntent references must cover the amount due; a manually marked paid status alone is insufficient. Stripe-confirmed zero-due credit settlements need no additional card charge. Card data and raw payloads are never saved to Supabase.
- **Premium → Basic:** The authenticated account button confirms the intent and calls `POST /api/billing/downgrade` with an empty JSON body. The backend checks the fresh, app-owned, active quantity-one Premium subscription, confirmed paid Premium period, no pending payment/pause/cancellation and at least 60 seconds remaining. The downgrade boundary must equal the current paid-through and billing-period end. It creates a schedule **from the existing subscription**, then updates two phases: unchanged Premium until that boundary; Basic from the boundary with `duration[interval]=month` and `duration[interval_count]=1`, with `end_behavior=release` so Basic continues afterward. Both phase transitions and the update use `proration_behavior=none`; no immediate downgrade, refund or second subscription is created. Special discounts, additional tax settings or unfamiliar schedules require review rather than overwriting them. Store `scheduledPlan`, `scheduledAt` and schedule reference separately. Premium entitlement remains paid Premium during the current phase, with its original expiry. Future phases never grant or revoke current access. On Stripe's effective Basic phase, the ledger can become Basic; renewal access is not extended until payment is confirmed. If webhooks are delayed, the old paid-through boundary still prevents indefinite Premium access.
- **Canceled/replaced downgrade:** `POST /api/billing/cancel-downgrade` requires an empty body, current authentication and confirmation in the account UI. It releases only this application’s identified pending downgrade with `preserve_cancel_date=true`; it never calls the schedule cancellation endpoint, which would cancel the subscription. Repeated scheduling returns the existing intent; repeated cancellation is harmless. Re-read the subscription's current schedule, not the event's old schedule body. Removing/releasing the pending change clears the future fields while keeping paid Premium. A replacement records the new schedule/date. Actual cancellation/abortion that ends the subscription removes active access; cancel-at-period-end preserves already-paid time until expiry.
- **Basic → Premium:** `POST /api/billing/upgrade` accepts no client-selected customer, subscription, price or return URL. It validates the current Basic item and creates a Premium-only Portal confirmation flow. Portal prorations are invoiced immediately. Basic stays Basic while an upgrade invoice is unpaid or requires action. Only a confirmed paid Premium invoice can elevate access. The original paid Basic period is preserved during a failed upgrade; an unpaid renewal cannot extend it.
- Failed, duplicate, late or reordered events always reconcile current provider state under the lease. Event creation time is audit metadata, not authority to overwrite newer state. Unknown customers cannot create memberships through webhook metadata. Unsupported prices, modes, invoices or multiple subscriptions fail closed. Return 2xx only after reconciliation commits; 5xx requests are retried by Stripe. Review webhook failures and use Stripe's redelivery controls; own-account status refresh also reconciles state.

The existing account page shows billing status, renewal/end date and a scheduled downgrade independently of its current paid plan. It has separate **Upgrade to Premium**, **Downgrade to Basic** and **Cancel pending downgrade** actions when applicable. Scheduling and canceling require explicit browser confirmation, show a result and retain Premium access. Manage Billing opens only that authenticated customer's management Portal session.

Stripe [cannot update or cancel a scheduled subscription in the Portal](https://docs.stripe.com/customer-management#limitations). While a downgrade is pending, invoices/payment methods remain available; the account explains that customers must first cancel the pending downgrade, then use Manage Billing to cancel the subscription. Once the Basic phase has taken effect, opening billing management or upgrading releases only the application's remaining Basic continuation schedule before opening the Portal. This leaves the Basic subscription running and preserves any provider cancellation date. Unknown schedules are not released.

The existing per-customer database lease serializes schedule mutations and webhook reconciliation. Stripe create/update/release requests carry stable idempotency keys. The create key includes the sorted terminal-schedule IDs for this subscription so canceling and then rescheduling creates a new schedule even within Stripe's idempotency window, including cycles in the same second. Bounded customer schedule-history reads fail for truncation. An ambiguous create is recovered by replaying the exact `from_subscription` request and requiring the same attached schedule ID before writing phases; an unrelated bare schedule cannot be claimed.
