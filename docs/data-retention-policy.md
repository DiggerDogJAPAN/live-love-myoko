# Love Live Myoko internal data retention policy

Prepared 31 October 2026 for MYOKO WORKS LLC. **Production rollout approved by the owner on 31 October 2026; automatic cleanup remains disabled and cleanup credentials must not be provisioned yet.** Responsible owner: the existing authorised administrator, with an owner-designated alternate. An alternate and mailbox owner still need to be assigned; no person is appointed automatically by this document.

Read with [the request/deletion runbook](privacy-requests-and-deletion.md) and the existing local audit snapshot at `docs/privacy-data-inventory.md` (not included in this release). The proposed 90-day and three-year periods supplied for this task are implemented as described below; scheduled enforcement is disabled pending further approval. Provider-controlled periods are not assumed. Legal holds and applicable legal duties override routine cleanup; record the reason and review it regularly.

## Categories, purposes and disposal

| Category / actual stored data | Purpose and location | Period / criterion | Removal method | Responsibility |
|---|---|---|---|---|
| Active account: ID, name, email, verification/authentication data | Supabase Auth; access and account operation | While active and needed; review dormant-account handling separately | Verified closure procedure deletes Auth row and linked application records; provider logs/copies handled separately | Authorised administrator |
| Deleted account application information | Auth/Finder records and any external correspondence/provider copies | Delete or minimise on verified processing unless a specific legal/security/dispute duty requires retention | Atomic database deletion after identity, billing, hold and dependency review; retain only necessary records separately before deletion; do not override a hold | Processing administrator |
| Membership status, tier, access/payment flags and paid-through dates | `finder_security.memberships`; server-side entitlement | Service lifetime, then reviewed closure; legally necessary billing records need separate preservation | Existing Auth FK cascade deletes this operational row on approved closure. Active/remaining paid access blocks the current deletion procedure | Administrator; accountant for transaction obligations |
| Saved properties and operation counters | `saved_properties`, `saved_property_limits`; user favourites and usage limits | While relevant to account; delete at account deletion | Existing user FK cascades; customer may remove individual saves through existing controls | Administrator / customer controls |
| Alert preferences: enabled flag, areas and opt-in/newness timestamps | `alert_preferences`; requested notifications | While needed for alerts/account; remove on account deletion | Existing user FK cascade; switching alerts off stops eligible delivery but is not immediate history erasure | Administrator / customer controls |
| Resolved Property Alerts delivery history: recipient email, frozen listing payload, attempts/status/provider receipt | `alert_deliveries`; delivery reliability and enquiries | **90 days**, measured from the latest of creation, sent time and last attempt. Only terminal `sent`/`cancelled` rows qualify | Bounded cleanup deletes the complete row. Pending/uncertain jobs, any open privacy request for the user and legal/investigation holds prevent cleanup | Dedicated retention role, supervised by administrator |
| Minimal unsubscribe proof: delivery UUID, user UUID, expiry | `finder_privacy.alert_unsubscribe_receipts`; preserve existing signed links when full delivery history is removed | Until the existing **180-day link expiry**, derived from original delivery creation; no email/payload stored | Cleanup copies only these fields before deleting qualifying history; removes expired proofs unless a hold/open request applies; Auth cascade removes them at account deletion | Dedicated retention role / administrator |
| Minimal notification markers: user UUID, listing UUID, notification date, optional delivery reference | `alert_notified`; prevent repeat notifications and old-inventory backfill | As long as needed for the account's alert relationship; no time-only expiry while the account exists | History deletion sets delivery reference NULL, preserving suppression. Markers cascade on verified account deletion. Never bulk-expire markers as part of routine history cleanup | Administrator; no time-based marker purge |
| Privacy request and processing records: case UUID, user link while account exists, type/scope, dates/status, necessary outcome/reviewer information | `finder_privacy.requests` / `events`; fulfil requests and demonstrate handling | Necessary active processing, then **up to three years from closure**, with earlier minimisation where possible. Escalate old active cases; do not purge them automatically | Reviewed completion/rejection removes original explanatory details unless held. Keep concise factual action/response notes. Account deletion additionally removes customer UUID/nonce and all case free text. Review and purge expired closed cases/events manually, after hold/legal checks | Administrator; no scheduled request-record deletion |
| Retention holds: user ID, reason and review timestamp | `finder_privacy.holds` or request `legal_hold`; preserve necessary evidence | While the documented obligation/investigation remains, with periodic review | Authorised administrator/operator releases a hold after review, not merely because a request is closed | Responsible case administrator |
| Application-controlled security logs | Minimal allowlisted operational diagnostics; any business-controlled exported log files | **Target 90 days**, except justified incident/legal holds | No new security-log database is introduced. Apply the period to controlled files/stores when configured; this task does not silently alter vendor log settings | Operator responsible for that store |
| Enquiry correspondence | Existing business mailbox providers; customer service and transaction records | As long as reasonably necessary for the enquiry, service, transaction or legal purpose | Manual mailbox/archive review and provider-supported removal; successful transaction/dispute files may require a different period | Monitored mailbox owner, to be confirmed |
| Payment/subscription/invoice records | Future Stripe integration and any accounting system | Applicable Japanese accounting/tax/legal requirements; exact classification/period must be confirmed before billing is implemented | Separate necessary accounting records from operational profile data; an Auth cascade is not authority to erase required invoices or cancel billing | Accountant and administrator |
| Individual privacy export working files | Administrator's protected local storage; preparation and verified release | Only for preparation/secure delivery and necessary case handling; remove redundant copies after use unless held | Save outside Git/CMS/public export; delete working copy after verified handoff/closure as appropriate. Minimise any necessary retained evidence | Exporting administrator |
| Backups | Supabase/provider/local machine/CMS backup systems as actually configured | Verified provider retention/expiry and justified recovery needs; **not yet independently confirmed** | Provider lifecycle, restricted restore access and deletion/revocation replay after restore; never claim immediate deletion from immutable copies | Backup owner / provider |
| Minimal deletion/revocation restoration instructions | Restricted operator recovery record, separate from the minimised customer case | Only while needed to prevent an older backup restoring a closed account; actual expiry depends on verified backup lifecycles | Record only the target UUID, deletion date and necessary recovery action before closure; replay after restore and remove when no relevant backup remains, unless legally held. Never store in Git/public exports | Backup owner and processing administrator |

The short unsubscribe-proof exception is essential: deleting all traces of a 91-day-old delivery would break a still-valid unsubscribe link. It is not retention of the old email or property snapshot. Similarly, removing per-listing notification markers could resend old inventory. These minimal records are distinguished from the 90-day delivery-history payload.

## Holds and unresolved records

- Any `pending`/`in_progress` privacy request protects that account's delivery history from cleanup. `legal_hold=true` continues that protection even after closure. Original request details are not minimised while that case's hold remains.
- Operator holds cover investigations without a customer request. Before installing a new hold, use the same per-account advisory lock as the runbook describes. Cleanup rechecks holds under that lock; do not bypass the protocol with an uncoordinated direct write.
- `pending` or `uncertain` email deliveries are never age-purged. Review stuck/uncertain jobs with the existing alert-delivery procedure and provider evidence. Do not invent a sent receipt or discard ambiguous delivery state to unblock deletion.
- Review hold purpose and necessity regularly. A hold is not permission to retain unrelated information indefinitely. Account deletion is blocked while any associated hold exists.

## Automatic cleanup boundaries

`public.finder_privacy_cleanup()` is executable only by the new restricted `finder_privacy_retention_worker` role (and its owner). The role has no password at installation and no direct private-table access, export capability or account deletion RPC grant. Each call considers up to 100 eligible accounts and removes at most 1,000 delivery rows and 1,000 expired proofs. The Python runner makes at most ten calls, stopping when no work remains, and logs aggregate counts only.

The separate GitHub workflow is scheduled daily at approximately 04:32 JST and gated by `FINDER_PRIVACY_RETENTION_ENABLED=true`. GitHub may delay scheduled jobs. It remains inactive until explicitly configured and approved. It uses its own database URL secret and verified CA certificate, not the crawler database credential or a browser/service-role key. TLS certificate and hostname verification are mandatory.

This mechanism does **not** delete accounts, privacy cases, notification markers, crawler/public listings, external emails, provider logs or backups. Repeated calls are safe. Counts of zero are a valid result; they do not prove every provider copy was removed.

## Manual privacy-record expiry review

Review closed cases once their completion date reaches three years, and earlier where their contents are no longer necessary. Confirm no hold, complaint, investigation or applicable retention duty remains. Record a minimal aggregate disposal summary in the restricted operations record, then remove only the individually reviewed case rows; their event rows cascade. Do not enable a blanket scheduled delete for this table. If case details were held at closure, explicitly review/release the hold and save the closed case again to minimise its original explanation.

Keep outcome/action notes short and factual. Do not copy passports, full correspondence, billing exports or detailed allegations into administrator notes. The UI cannot decide legal necessity on the administrator's behalf.
